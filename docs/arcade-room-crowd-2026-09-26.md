# Living arcade crowd — September 26, 2026

Local, not deployed. `lib/arcade/arcadeRoomCrowd.ts` creates three native bean visitors on mobile, five on desktop. Casual clothes, screen-facing console reaches, staggered play sessions and small pleased gestures make the football arcade visibly occupied. Visitors reserve cabinet stations and travel through outward approach and central-aisle waypoints before trying another cabinet. Near the main player they move sideways from the console or stop a crossing, preserving human access.

The renderer supplies actual cabinet positions/yaws and movement bounds. It alone calls `update(dt,time,playerX,playerZ)` and `dispose()`. The crowd has no timer, listener, renderer, audio or Town runtime import. A stable `debugStates` array supports integration checks without per-frame allocations. The owner must stop updates when hidden and dispose the room when a game opens.

Added runtime work: 3/5 existing native rigs, one pooled shadow geometry/material with one shadow per visitor, and a bounded pairwise separation pass. Console hand motion uses cached joints after the existing native pose; feet and locomotion stay solver-driven. Reduced-motion mode suppresses the hand pulses and pleased wave. The parent may run the visible room at 15fps idle/30fps moving; the helper accepts that cadence. Continuous visible activity is intentional for this user request. No claim about physical phone temperature.

`node tests/arcade-room-crowd.cjs` runs 100 simulated seconds in each responsive layout at 15 and 30fps using actual native rigs. It checks bounds/finite positions, cabinet changes, each route phase, stable debug objects, player yielding and complete/idempotent disposal. These deterministic checks passed. TypeScript passed before the final cached console-arm overlay; the integration owner runs the final shared check. Visual room/camera readability and hidden/game-open lifecycle are the integrated renderer owner's browser checks, not established by the simulation alone.

Larger shared world follow-up: the final visitor starts at (2,8) for bounds x ±14 / z −11…12, beside the entry at (0,9), and walks through the central aisle toward its reserved cabinet. Mobile and desktop use identical world coordinates, with only visitor count reduced on mobile. # Follow-up: greetings and body spacing

Visitors now briefly acknowledge an approaching player with a head turn, happy expression and the native raised-hand channel. A 1.4-second gesture, eight-second cooldown and distance hysteresis prevent constant repeated waving. Console reach yields to that gesture; no additional actors are created.

All moving visitors steer to their right around oncoming traffic, including stationary visitors. A positional separation guard maintains 0.84 m between their roots; actual corrected displacement drives gait velocity. The previous older-actor priority allowed one visitor to walk through another and has been removed. The existing route/yield/disposal test now samples every pair for non-overlap over 100 seconds at 15, 30 and 60 Hz for both three- and five-visitor configurations. All pass, including finite greetings and continued cabinet visits.

Room player actions follow-up: the scene now exposes jump, wave, scan and celebrate. F uses native Scan (1.4 seconds); C uses native Airplane (2.6 seconds), with durations from SKILL_MOVES. Existing Space jump and Q wave remain. One reused SkillMotion record drives the new actions through the existing native rig and parent room clock. A different input interrupts a wave, scan or celebration immediately, while repeating the active action does not restart it. Airborne jumps finish before another action begins, preserving their landing. Debug scan/celebrate ages are available to the real-touch integration tests. UI layout/buttons are owned by the parent integration lane.
