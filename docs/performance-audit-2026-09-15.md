# Whole-app performance audit — September 15, 2026

Read-only implementation audit. No application code or deployment changed by this audit. Reviewed `AGENTS.md`, `performance-guide.md`, dated measurements, main island loop, rendering helpers, field runtime, arcade games, previews, UI subscriptions, audio and network paths. Recommendations below are opportunities, not measured iPhone cooling. A separate agent is investigating the newest live-knockout effects; those changes are not duplicated here.

## Conclusion

The app already implements many established mobile-game optimizations. The next useful work is **consistent inactive-state handling across every game, eliminating repeat preview generation, and reducing hot-loop allocation**, followed by measured shadow/GPU experiments. Repeating generic “pool particles / cap FPS / batch meshes / pause background tabs” advice would overlook work already done.

The main island remains a continuously rendered, shadowed 3D scene while moving. Comparing its warmth with a mostly static application is not an equivalent workload. No competitor was instrumented; comparisons here are against documented browser/engine practices, not unsupported claims that another named game uses less power.

## Rendering and GPU investigation

Already present: DPR capped at 2, mobile island rendering near 30 Hz, 60 Hz player simulation, 2048 shadows, 50 m scenery chunks, shared palette geometry, static shadow batches, shadow-volume culling, hidden-transform gates, pooled effects, offscreen NPC pose suppression and shared live-player instancing. These align with engine guidance to reduce draw submissions. [Three.js object optimization](https://threejs.org/manual/en/optimize-lots-of-objects.html).

The strongest existing GPU evidence remains the dated shadow comparison: normal 7.455 ms, culled 6.790 ms, framebuffer-copy cached 10.182 ms in its controlled local sample. **Do not re-enable the rejected mobile framebuffer-copy cache.** Do not reduce DPR, shadow resolution or teaching cues as an unannounced fix.

New experiments worth evaluating, in order:

1. Measure color and shadow passes separately on the same route, with the newest cage visible/offscreen. Check shadow caster geometry and transparent overlap before changing effects. The heat agent owns the live-knockout audit.
2. Reuse precomputed shadow extrusion bounds in `shadowVisibility.ts:14–18` when sun direction/geometry is unchanged. Frustum tests must still follow camera movement. Likely modest CPU savings; retain offscreen shadows entering the view.
3. Investigate static-shadow rendering into a dedicated reusable target only as a separate architectural experiment with real iOS GPU measurements. The prior framebuffer-copy regression is evidence against casually retrying this; unchanged visual output and dynamic receiver correctness are mandatory.
4. Inspect compositing cost of `FieldTranscript.module.css:2` (22 px backdrop blur over moving content) and other overlays. No blanket removal: measure visible panel GPU time first and compare an equivalent precomposited/static background where island rendering is already frozen.

MDN recommends batching submissions, avoiding synchronous GPU queries/readbacks and explicit resource lifetime management. Its smaller-backbuffer option is a quality tradeoff, not the default recommendation for this app. [WebGL practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).

## Loading and assets

The local existing production artifacts contain a 5,097,233-byte chunk (`512…js`, gzip estimate 1,115,348 bytes), a 729,189-byte page chunk (gzip 248,258), and a 539,860-byte shared chunk (gzip 133,767). These are file measurements, **not actual network transfer totals**, and the artifact may predate today's edits. Breakaway imports the Babylon core namespace; its engine dependency is a candidate for the large deferred chunk, but confirm module attribution with a bundle analyzer before claiming exact ownership.

Arcade games and LiveArcadeMatch already use `next/dynamic`; the large deferred chunk should not be labeled initial island download without a cold-load network trace. More Town menu modules remain static imports (`Town.tsx:23–36`). Candidate work: lazy-load secondary drawers and their data only on first use, keep lightweight shells/fallbacks responsive, and inspect selective Babylon module imports. No engine rewrite is justified by bundle size alone. [Next.js lazy loading](https://nextjs.org/docs/app/guides/lazy-loading).

`public/voice` occupies roughly 130 MB on disk, music 8.9 MB and lessons 2.2 MB. That does not mean these are loaded eagerly. Music uses `preload='none'`; verify lesson voice network selection rather than mass-converting files. Cold/warm tests should record JS bytes, startup tasks, voice fetches and first playable frame separately from steady-state flight.

World generation builds and clones geometry before merging (`world.ts:928–950`). Profile startup peak heap and construction tasks; build-generated static geometry could remove startup CPU/duplication, but would add transfer/cache/versioning costs. This is a longer-term startup experiment, not a presumed fix for five-minute warmth.

## Memory and lifecycle

Explicit renderer/geometry/material cleanup is widespread; previews also force context loss. Costume snapshots have a one-appearance cache, rather than unbounded history. Audio shares its context and disposes media/voices. No leak was proven by this code audit.

Run a repeated lifecycle test: 20 cycles through store, mascot stories, customizer, live match and each arcade game, returning to the same island view. Record retained canvases, active rAFs/listeners, renderer texture/geometry counts and heap snapshots after settling. Look for an increasing baseline, not temporary peak allocations. Verify texture ownership separately because disposing a material does not dispose its textures. [Three.js disposal guidance](https://threejs.org/manual/en/how-to-dispose-of-objects.html).

## Updated priority: load the current experience and its likely next step

The user's preferred direction is staged loading. Implement this first for menus, previews and lesson media, where boundaries already exist; investigate world streaming separately. **Not drawn, not constructed, not downloaded and not GPU-resident are different states.** Frustum culling reduces drawing but does not undo the CPU construction of geometry or release buffers already uploaded. A hidden object can still own memory.

### What the code actually loads now

- `Town.tsx:226–242` builds the whole procedural town, all field surfaces, match runtimes, spatial collision metadata, coach practice and knockout objects during scene initialization. `world.ts:928–950` constructs/clones/merges scenery into 50 m spatial batches. These chunks are rendering units, not independent downloads. Changing their visibility does not turn the current implementation into asset streaming.
- `fieldRuntime.ts:26,60` creates simulation entries for all venues immediately but creates individual player rigs on first visible use. Keep that useful deferred rig behavior.
- `vehicle.ts:8–148` creates multiple ride variants, then toggles their visibility. Selected ride and mode are known, so deferred construction of unused variants is possible, but must retain fast switching and correct disposal.
- Secondary Town drawers are mostly statically imported. Arcade minigames are already split with `next/dynamic`; their code should stay unloaded until selected rather than preloading every game merely because the arcade is nearby.
- `formatLessons.ts:14` already fetches and caches only the requested **format** JSON. That JSON contains the full lesson/quiz/voice manifest for the format. It does not download every voice recording. `FieldLearning.tsx:35` requests this when the selected format mounts.
- `useLessonVoice.ts:12` assigns only the selected line and coach recording to one reused audio element. There is no next-line warming yet; setting a source can still request a clip when narration is disabled, so the loader should explicitly avoid unnecessary muted narration fetches.
- Store displays the selected category (`IslandStore.tsx:33`), but ordinary previews generate **every category** (`useStorePreviews` called without an item filter). Costume previews likewise capture the whole collection for the current appearance. This is the clearest mismatch between visible content and preparation work.

### Near-term staged-loading plan

| Stage | Load now | Prepare next | Leave unloaded |
|---|---|---|---|
| Initial island | Main scene, equipped character/ride, movement and collision logic, essential HUD, first onboarding screen | Following onboarding component after first usable frame; one likely nearby interaction shell after idle time | Store snapshot generation, unused game engines, full costume imagery, unselected lesson audio |
| Store open | Selected category metadata and visible card images | One additional scroll row; optionally adjacent category after settling | Other categories' preview renders and all unrelated costume snapshots |
| Mascot collection | Visible cards for current appearance, then next row | Selected story after card focus/intent | Entire collection's 3D snapshots on every appearance change |

| Arcade menu | Lightweight game cards | Selected game's module on pointer/focus intent; for touch, begin immediately on selection with a responsive loading shell | All three games on menu open or proximity alone |
| Equipment switch | Current equipped variant | User-selected next variant while equip confirmation/transition displays | Never-used vehicle variants; retain recently used variant to make toggling quick |

Suggested starting budgets are **tunable experiments, not known device limits**: one speculative network request at a time; at most one narration clip ahead; preview generation at most one card per rendered frame and only if the prior frame stayed within budget; cancel queued preview work when category closes. Cache equipment images by visual-version/item ID and mascot images by visual-version/appearance/item ID. A bounded 32-card recent-image cache is a reasonable initial test, not permission for unbounded base64 accumulation. Prefer static generated images for fixed equipment; retain live preview only where the user's appearance makes it necessary.

Pause speculative preparation during boost, active lesson interaction or sustained slow frames. On browsers without supported connection hints, use conservative defaults rather than assuming fast Wi-Fi. Cache actual completed results; canceling a request must not leave a rejected promise permanently cached. Do not rely on aborting dynamic imports—the request may already be underway—so schedule those only on strong intent. Stage data/loading indicators without exposing answers before a quiz choice.

### World loading is a larger architectural change

Keep lightweight **whole-island metadata** resident: collision rectangles, stairs/roof support, ramps, collectible IDs/state, route graphs, destinations and map outlines. Separate that metadata from visual mesh creation. The player must not fall through an unseen rooftop or lose a moving truck because its render chunk was discarded.

Introduce visual chunk factories and explicit lifecycle states: metadata-only → queued → CPU-ready → GPU-ready → visible → recently-used → evictable. First reuse the existing 50 m cells; do not repeat the rejected 25 m chunk experiment. Preserve cross-cell shared geometry/material ownership and release only resources no retained chunk references. `staticShadowBatches`, `shadowVisibility` and `hiddenTransformGate` currently register known scene objects at creation: streaming requires explicit registration/removal APIs, otherwise late chunks can bypass batching, culling or transform handling.

Determine required chunks from the **camera frustum plus shadow contributors**, not just player distance. The sun is angled, so a building outside the screen may cast a visible shadow. Elevated flight expands the visible ground area. Include nearby collisions/interactions in metadata regardless of mesh visibility; keep active projectiles and their gameplay state independent of render residency.

An initial predictive envelope to measure: current visible cells plus a one-cell surrounding band, then a movement-direction corridor sized from **actual current velocity × measured p95 preparation time**, with at least two seconds of look-ahead during ordinary flight. Base jetpack speed is 34 m/s (`travelModes.ts:8`), so two seconds already means about 68 m before boost; use actual boosted velocity, not that base constant. Widen the side/rear buffer while turning. Add a 5–10 second recently-visible retention window to prevent repeated unload/rebuild around a border. These values must expand if first-use GPU upload/compile time is longer or top-down camera coverage is larger.

Prepare visible-adjacent chunks before they enter view, spread CPU creation over measured small tasks (initial target ≤2 ms each), and warm necessary shaders/uploads gradually. Merely constructing hidden meshes does not prove the GPU is ready. Avoid allocating a second full renderer just to warm them. Teleports and map travel need a destination-ready barrier: prepare destination during the existing transition, then move the player. Never show blank scenery, remove collision protection or trap input while completing an unbounded build task.

Eviction should begin with least-recently-used **offscreen visual** chunks outside the shadow/prediction margin. Keep scene infrastructure, materials used elsewhere and player/lesson assets pinned. Record estimated geometry bytes (attribute/index arrays), texture dimensions/formats and retained chunks; there is no reliable universal browser GPU-memory meter. Start with the current scene's measured memory as a baseline, then tune residency limits on the physical phone. Avoid claiming that a lower JS heap necessarily means lower GPU memory.

### Acceptance measurements for staged loading

Record separate cold start, warm start, first interaction and sustained-travel results. Verify: fewer startup tasks/bytes; zero unrelated game requests before selection; no off-category preview renders; one current plus at most one speculative voice clip; no scene holes during maximum boost, hard turns or parachute descent; no stalls when reentering recent areas; stable memory after repeated district travel; correct shadows, stairs, projectiles and moving-truck landings. Compare p95 input-to-visible response and long frames, not just average FPS. A streaming system that creates frequent upload spikes can feel worse and use more power than retaining this relatively small island—keep the architectural change only if its measured savings exceed churn and complexity.

Recommended execution order: **selected-category/visible-row previews → deferred drawers and unused ride variants → current/next narration discipline → prototype one district's visual lifecycle → expand world streaming only after the prototype beats the resident-world baseline.** The first three can improve readiness and unnecessary work without redesigning island physics or reducing visual quality.
